# ROLLBACK_STANDARD.md — 롤백 표준 (Phase 6)

- 상태: ACTIVE (Phase 6)
- 관련 도구: `scripts/verify_release.py` (`rollback_point` 검사)
- 관련 문서: `docs/RELEASE_STANDARD.md`, `templates/RUNBOOK.md`, `templates/DEPLOY_LOG.md`
- 근거: `FLASH_BUILD_PROMPT.md` §8 (롤백 표준)

## 1. 핵심 원칙

**롤백할 수 없는 변경은 라이브에 적용하지 않는다.**

되돌릴 방법이 없는 변경(예: 복원 불가능한 마이그레이션, 삭제된 백업, 기록되지
않은 설정 변경)은 검증을 통과했더라도 배포 대상이 아니다. `verify_release.py` 는
`require_rollback=true` 인 프로젝트에서 `rollback_point` 가 비어 있으면 릴리스
자체를 FAIL 로 차단한다.

## 2. 최소 보존 대상

배포마다 다음을 최소한 보존한다.

```text
- 직전 정상 실행파일
- 직전 정상 설치파일
- 직전 정상 manifest
- 직전 정상 설정
- 직전 정상 커밋
- 마이그레이션 전 데이터 백업
```

이 목록은 "있으면 좋다"가 아니라 배포 전 필수 조건이다. 어느 하나라도 없으면
`rollback_point` 를 신뢰할 수 없다.

## 3. 코드 롤백과 데이터 롤백을 분리한다

코드(실행파일, 설정, manifest)와 데이터(DB, 사용자 파일, 마이그레이션 결과)는
되돌리는 방법과 시점이 다르다.

| 구분 | 롤백 방법 | 주의점 |
|---|---|---|
| 코드 롤백 | 직전 정상 실행파일/설치파일로 교체, 직전 정상 커밋으로 배포 재실행 | 코드만 되돌리면 새 스키마를 기대하는 이전 코드가 깨질 수 있다 |
| 데이터 롤백 | 마이그레이션 전 백업에서 복원 | 되돌릴 수 없는 파괴적 변경(컬럼 삭제 등)은 별도 계획 없이 진행하지 않는다 |

코드 롤백만으로 데이터 문제를 해결하려 하지 않는다. 반대로 데이터를 되돌리면서
코드는 최신 상태로 남겨두면 스키마 불일치가 발생할 수 있으므로, 롤백 절차서
(`templates/RUNBOOK.md`)에 두 롤백의 순서와 조합을 명시한다.

## 4. 업데이트 실패 시 기존 정상 버전을 보존한다

- 새 버전 배포가 실패하면 자동으로 이전 정상 버전 상태를 유지한다.
- "일단 배포하고 나중에 고친다"를 기본 전략으로 삼지 않는다.
- 부분 배포(일부 파일만 갱신된 상태)를 라이브 상태로 남기지 않는다.

## 5. 실패 버전을 무한 재시도하지 않는다

- 자동 복구/재시도 로직은 상한 횟수와 백오프를 둔다.
- 같은 실패 버전을 계속 재배포/재시작하는 루프는 사람이 개입할 때까지 멈춘다.
- 재시도 상한에 도달하면 알림을 남기고 직전 정상 버전으로 고정한다.

## 6. DB 마이그레이션 전 백업과 복원 테스트

- 마이그레이션 실행 전 백업을 만든다. 백업이 없으면 마이그레이션을 실행하지 않는다.
- 백업은 만든 뒤 최소 1회 복원 가능한지 검증한다(복원 테스트 없는 백업은 없는
  백업과 같다고 가정한다).
- 되돌릴 수 없는 마이그레이션(컬럼 삭제, 데이터 손실을 동반하는 변환)은
  가능하면 되돌릴 수 있는 단계(추가 → 이행 → 검증 → 이전 컬럼 제거)로 나눈다.
- 마이그레이션 실패 시 자동으로 백업 복원을 시도하지 않는다. 사람이 상태를
  확인한 뒤 복원 여부를 결정한다(자동 데이터 삭제·복원은 변조 감지를
  이유로도 하지 않는다).

## 7. verify_release 와의 연결

`rollback_point` 검사(`scripts/verify_release.py`)는 이 표준을 자동 검사로
연결하는 유일한 지점이다.

- `require_rollback=true` + `rollback_point` 빈 값 → FAIL (릴리스 차단)
- `require_rollback=false` + `rollback_point` 빈 값 → PASS 하되 세부사항에 경고를
  남긴다 (자동 검사가 강제하지 않는 프로젝트도 있을 수 있으나 권장하지는 않는다)

`rollback_point` 값 자체(커밋 해시, 태그, 이전 배포 식별자)가 실제로 유효한지는
이 도구가 검증하지 않는다 — 그 값이 가리키는 산출물이 §2 의 최소 보존 대상에
실제로 존재하는지는 배포 담당자가 확인한다.
