# MIGRATION_GUIDE.md — 기존 프로젝트 점진적 적용 (Phase 7)

- 상태: ACTIVE (Phase 7)
- 근거: `FLASH_BUILD_PROMPT.md` §3.4, `docs/DECISIONS/ADR-0001-layered-coordinator.md` §6
- 실행 가능 예제: `examples/existing-project-migration/`

## 1. 핵심 원칙

**한 번에 전면 재작성하지 않는다.** 기존 정상 동작을 보존하면서 점진적으로
개선한다. 이름보다 책임과 단일 소유권을 우선한다 — 기존 프로젝트에 같은 책임의
클래스(Manager, Controller, Service 등)가 이미 있으면 재사용하고 새로 만들지
않는다.

## 2. 8단계 절차

각 단계는 산출물(문서 또는 코드)을 남긴다. 산출물 없이 다음 단계로 넘어가지
않는다 — "조사했다"는 진술만으로는 부족하다.

### 2.1 현재 호출 경로 조사

- **목표:** UI/Route가 어디서 DB·외부 API·파일을 직접 호출하는지 찾는다.
- **방법:** 데이터베이스 드라이버, HTTP 클라이언트, 파일 I/O 함수의 호출부를
  전수 검색한다 (예: `grep`/IDE 검색으로 import 사용처 추적).
- **산출물:** 직접 호출 경로 목록 (파일:줄, 호출 대상, 호출 계층).
- **예제 대응:** `examples/existing-project-migration/before/app.py` 의
  `get_order_status_for_display()`가 `_fake_order_api()`를 직접 부르는 지점.
- **중단 조건:** 직접 호출 경로가 하나도 없으면(이미 계층화되어 있으면) 이후
  단계 상당수를 생략할 수 있다 — 이 경우 §3(중앙화할 경계)만 재확인한다.

### 2.2 상태 소유자 조사

- **목표:** 같은 정보(캐시, 세션, 설정값 등)를 몇 곳에서 보관하는지 찾는다.
- **방법:** 같은 도메인 데이터를 가리키는 변수/필드/캐시를 모듈별로 나열하고
  중복 여부를 비교한다.
- **산출물:** 상태별 현재 소유자(들) 목록. 소유자가 둘 이상이면 표시한다.
- **예제 대응:** `before/app.py` 의 `_ui_status_cache`와 `_recent_lookups`가
  같은 조회 결과를 중복 보관한다.

### 2.3 직접 호출과 우회 경로 목록화

- **목표:** 2.1의 경로 중 "표준 경로를 우회하는" 것을 표시한다 (예: 이미
  Repository가 있는데 일부 코드만 DB 드라이버를 직접 쓰는 경우).
- **산출물:** 우회 경로 목록 + 각 경로의 위험도(예: 인증/결제/저장이면 높음).

### 2.4 기존 Coordinator/Gateway 재사용 판단

- **목표:** 새 Coordinator를 만들기 전에 같은 책임을 가진 기존 클래스가 있는지
  확인한다.
- **판단 기준:** `docs/ARCHITECTURE_STANDARD.md` §2·§3, 새 오케스트레이터 생성
  금지 조건은 `SKILL.md` §6.
- **산출물:** "재사용" 또는 "신규 생성 + 근거" 결정 기록 (가능하면 ADR,
  `templates/ADR_TEMPLATE.md` 사용).

### 2.5 위험 경계부터 중앙화

- **목표:** 모든 경로를 한 번에 옮기지 않고, 위험이 큰 경계(인증, 결제, 외부
  네트워크, DB 쓰기, 비밀정보 저장)부터 먼저 단일 소유자를 만든다.
- **산출물:** 새/재사용 Adapter(또는 Gateway) 1개 + 그것을 쓰는 호출부 전환.
- **예제 대응:** `after/order_api_adapter.py` — 외부 주문 API 접근을
  `OrderApiAdapter` 하나로 모은다.
- **중단 조건:** 중앙화 대상 경계가 기존 테스트로 보호되지 않으면, 먼저 회귀
  테스트를 추가한 뒤 진행한다(순서를 바꾸지 않는다).

### 2.6 기능별 점진적 이전

- **목표:** 도메인/기능 단위로 하나씩 옮긴다. 여러 도메인을 동시에 건드리지
  않는다.
- **산출물:** 도메인별 Coordinator/Service 전환 완료 목록 + 남은 도메인 목록.
- **예제 대응:** `after/order_coordinator.py`, `after/order_service.py` —
  order 도메인 하나만 전환했고, 이 예제에는 다른 도메인이 없다(최소 예제이므로).

### 2.7 회귀 테스트

- **목표:** 이전 전후 동작이 같은지 확인한다 (의도한 개선 외에는 동작이
  바뀌지 않아야 한다).
- **방법:** 기존 테스트가 있으면 그대로 실행하고, 없으면 최소한 "같은 입력 →
  같은 결과" 를 수동으로 대조한다.
- **예제 대응:** `before/app.py`와 `after/main.py`를 각각 같은 입력
  (`A100`, `A101`, `A999`)으로 실행해 실질적 동작(정상 조회 2건, 존재하지
  않는 주문 1건 실패)이 같음을 확인한다 (`docs/EXAMPLES.md` 실행 명령 참고).
- **중단 조건:** 회귀 테스트가 실패하면 다음 단계(레거시 경로 제거)로 넘어가지
  않는다. 원인을 해결하거나 해당 도메인만 이전 전 상태로 되돌린다.

### 2.8 레거시 경로 제거

- **목표:** 새 경로로 완전히 옮긴 뒤에만 옛 직접 호출 경로를 제거한다.
- **산출물:** 제거된 경로 목록 + 제거 시점의 커밋/체크포인트.
- **주의:** 레거시 경로를 "일단 남겨두고 새 경로와 병행"하는 기간이 길어지면
  상태 중복이 재발한다. 병행 기간에는 §2.2에서 찾은 문제가 다시 생기지 않는지
  주기적으로 재확인한다.

## 3. 각 단계 공통 중단 조건

- 조사 없이(2.1~2.3을 건너뛰고) 바로 새 Coordinator를 만들지 않는다.
- 한 커밋/한 세션에서 여러 도메인을 동시에 이전하지 않는다.
- 회귀 테스트 없이 레거시 경로를 제거하지 않는다.
- 기존 정상 동작이 깨지면 즉시 멈추고 체크포인트(`scripts/checkpoint.py`) 또는
  직전 정상 커밋으로 되돌릴 수 있는지 먼저 확인한다.
