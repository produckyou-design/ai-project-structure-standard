# ADR-0001: 계층형 Domain Coordinator 채택

- 상태: ACCEPTED
- 날짜: 2026-08-04 (Phase 0)
- 결정자: AI Project Structure Standard 저장소 설계 세션

---

## 1. 맥락

AI가 장기간 소프트웨어 프로젝트를 개발할 때, 기능이 커질수록 상태 소유권이 흩어지고
직접 호출 경로(UI → DB, UI → 외부 API)가 늘어나며 회귀와 보안 경계 위반이 발생한다.
한편, 하나의 거대한 전역 오케스트레이터(GlobalOrchestrator)를 만들면
모든 기능 로직이 한 곳에 모여 수정 비용과 병목이 폭발적으로 증가한다.

## 2. 결정

**계층형 구조를 표준으로 채택한다.**

```text
UI / API / 외부 요청 / 백그라운드 작업
            |
  Application Entry Layer
            |
    Domain Coordinator
            |
  Domain Service / Use Case
            |
 Adapter / Repository / Gateway
            |
DB / 파일 / 외부 API / 운영체제 / 서버
```

- 도메인별 Coordinator(`AuthCoordinator`, `MarketDataCoordinator`, `NewsCoordinator` 등)를 둔다.
- Coordinator는 요청 정규화, 순서, 중복 병합, 상태, 캐시 정책, 타임아웃, 취소, 결과 조합, 오류 정규화만 담당한다.
- 실제 파일 처리, 네트워크 전송, DB 접근, 암호화, 파싱은 Service/Adapter/Repository/Gateway에 둔다.
- 순수 계산 함수는 Coordinator를 거치지 않는다.

## 3. 거대한 단일 오케스트레이터를 사용하지 않는 이유

- 모든 도메인의 상태와 기능이 한 클래스에 결합되어 단일 변경이 전체에 전파된다.
- 파악·테스트·회귀 방지가 어렵고, AI가 장기간 작업할 때 수정 우선순위를 판단하기 어렵다.
- 외부 경계(네트워크, DB, 인증)의 단일 소유권이 흐려져 보안 검증이 불가능해진다.
- 실패 지점이 하나로 집중되어 부분 복구와 롤백이 불가능해진다.

## 4. 계층형 Domain Coordinator를 채택한 이유

- 상태와 외부 경계에 단일 소유자를 부여할 수 있다.
- 도메인 단위로 교체·테스트·이전이 가능해 기존 프로젝트에 점진적으로 적용하기 좋다.
- Coordinator는 "통제"만 하고 "기능"은 하위 계층에 위임하므로 책임이 선명하다.
- 오류 정규화와 trace_id 유지 지점이 명확하다.

## 5. 최상위 Application Coordinator가 필요한 조건

필요한 경우에만 둔다. 담당 가능 범위:

- 앱 부팅, 앱 종료
- 로그인 이후 초기화
- 여러 도메인에 걸친 실행 순서
- 업데이트 후 재시작
- 전체 장애 복구 모드
- 사용자 또는 워크스페이스 전환

직접 수행하면 안 되는 것: DB 쿼리, 외부 API 파싱, 인증 세부 로직, 뉴스 처리, 결제 처리, 파일 저장, 기능별 캐시 관리.

## 6. 기존 프로젝트에서 점진적으로 적용하는 방법

1. 현재 호출 경로 조사
2. 상태 소유자 조사
3. 직접 호출과 우회 경로 목록화
4. 기존 Coordinator와 Gateway 재사용 판단
5. 위험 경계부터 중앙화
6. 기능별로 점진적 이전
7. 회귀 테스트
8. 레거시 경로 제거

이름보다 책임과 단일 소유권을 우선한다. 기존 정상 동작을 보존하며 한 번에 전면 재작성하지 않는다.

## 7. 포기한 대안

| 대안 | 포기 이유 |
|---|---|
| 거대한 GlobalOrchestrator | 결합도·병목·실패 집중 (3절) |
| Coordinator 없이 UI→계층 직접 호출 | 상태 소유권 분산, 검증 경계 부재 |
| 모든 함수를 Coordinator 경유 | 순수 계산까지 거치는 과도한 통제로 생산성 저하 |

## 8. 예상 위험

- Coordinator에 실제 기능 로직이 다시 쌓이는 리스크 → 책임 목록(5절·6절)을 문서화하고 500줄 초과 시 분리를 검토한다.
- 도메인 수가 늘면서 Coordinator 수도 늘어나는 리스크 → 중복 책임이 발견되면 `FILE_RESPONSIBILITIES.md`를 갱신하고 병합한다.
- 기존 프로젝트 이전 시 회귀 리스크 → 위험 경계부터 중앙화하고 단계별 회귀 테스트를 게이트로 한다.

## 9. 롤백 방법

- 코드 롤백: 직전 정상 커밋으로 `git revert` 또는 `git checkout` 후 회귀 테스트.
- 데이터 롤백: 마이그레이션 전 백업에서 복원 (코드 롤백과 분리).
- 구조 이전 중 실패 시 해당 도메인만 이전 전 상태로 복원하고 레거시 경로를 유지한다.
- 모든 변경은 체크포인트와 서명으로 추적되어 롤백 지점을 알 수 있다.

## 10. 결과

이 표준은 스킬 저장소의 `docs/ARCHITECTURE_STANDARD.md`, `SKILL.md`, 예제(3종)에 일관되게 반영된다.
새 오케스트레이터 생성은 위 조건(5절)을 만족할 때만 허용한다.
